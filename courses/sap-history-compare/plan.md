# 主要ERP比較とデータアーキテクチャの変遷

**前提コース:** [ゼロから完全理解！ERPの全体像と「SAP S/4HANA」徹底解剖](./sap-basic/plan.md) 修了者向け。S/4HANA の基本構成・コアモジュール・HANA DB の基礎（行指向/列指向、インメモリ、Universal Journal）を理解したうえで、ERP 比較とモダンデータ活用の全体像を深掘りする。

## 第1章：イントロダクション — なぜ「歴史とインフラ」から ERP を見るのか

- 単なるベンダー製品の機能比較にとどまらない学び方
- **インフラ・ハードウェアの進化**が ERP アーキテクチャ設計に与えた影響
- 現代の **Best of Breed（適材適所の組み合わせ）** 構成が最適解となりうる理由
- **Single Source of Truth** と **System of Record / System of Insight** の切り分け
- ゴール：顧客のビジネス特性とデータボリューム・コストのトレードオフを評価し、ERP 単体ではなく周辺エコシステムを含めた全体アーキテクチャの提案構想を描けるようになる

## 第2章：【歴史と構造】ハードウェア進化がもたらした「優先事項の逆転」

ERP の歴史は「ハードウェアの制約をいかに乗り越えるか」の歴史。昔と今では、データベース設計のセオリーが 180 度変わっている。

### 2000 年代まで（SAP R/3、従来型オンプレミス ERP）

- **ハードウェアの限界** — メモリ（RAM）が極めて高価。ディスク I/O（HDD への読み書き）が圧倒的なボトルネック
- **至上命題** — 「リソースの節約」と「OLTP（トランザクション処理）の保護」
- **極限の正規化** — データ重複を避け、ストレージ容量を節約
- **集計テーブルの乱立** — 明細からの都度計算は I/O がパンクするため、夜間バッチで「月次集計テーブル」を作成
- **分析の分離** — 基幹システムが止まるのを防ぐため、分析用途は外部 DWH へ夜間 ETL する「バッチ連携」が鉄則

### 2010 年代〜現在（S/4HANA、クラウド ERP の台頭）

- **ハードウェアのブレイクスルー** — メモリの大容量・低価格化。マルチコア CPU と NVMe SSD の普及
- **至上命題** — 「リアルタイム性の追求」と「データの即時利活用」
- **集計テーブルの廃止（Universal Journal / ACDOCA）** — 数億の明細からオンデマンドで瞬時に集計。事前バッチが不要に
- **列指向 DB への統合** — 特定列だけを高速スキャンし、同一 DB 上で OLTP と OLAP を同居（HTAP）させる

## 第3章：メガベンダー ERP の「出自」が紐解く構造的強みと課題

製品の歴史（出自）を知ることで、各社アーキテクチャの根本的な違いと「得意・不得意」が見えてくる。

### SAP S/4HANA — プロセス至上主義とインメモリの極致

- ドイツの製造業モデルから生まれた、全業務を一気通貫させる堅牢なアーキテクチャ
- **強み（Single Source of Truth）** — 全モジュールが単一のインメモリ DB（HANA）で動く。購買から会計への仕訳がタイムラグゼロ。Fit to Standard において右に出る者はいない
- **課題（Clean Core のジレンマとコスト）** — データ肥大化時の HANA 維持コスト。コアのカスタマイズはバージョンアップを困難にするため、周辺開発は SAP BTP 等へ逃がす必要

### Oracle ERP Cloud — DB ベンダーの買収戦略と最強の EPM

- 強力な DB 基盤を武器に、各領域のトップ製品を買収・統合してきた歴史
- **強み（経営管理・予実シミュレーション）** — Hyperion 統合の Oracle EPM は圧倒的。SAP が制度会計（標準化）に強いのに対し、Oracle は管理会計・将来予測（柔軟性）に強い
- **課題（モジュールのサイロ化）** — 裏側の DB 構造がモジュールごとに分散。マスター統合やリアルタイム同期の設計難易度が SAP より高い傾向

### Microsoft Dynamics 365 — 圧倒的な「ユーザー接点」とローコード

- **強み（フロントオフィス統合と AI）** — Office 365・Teams 連携。Power Platform による現場主導のローコード開発。UX と CRM 領域で最強クラス
- **課題（グローバル製造業等での実績）** — 超巨大企業の複雑な生産管理や、グローバル統合会計基盤としての堅牢性では SAP・Oracle に一日の長

## 第4章：現代の最適解「ハイブリッド・データアーキテクチャ」

なぜ S/4HANA や Oracle の機能だけですべてを完結させてはいけないのか。

### コンピュートとストレージの分離という新たなパラダイム

- S/4HANA（HANA DB）は超高速だが、計算（コンピュート）と保存（ストレージ）が密結合したインメモリ DB
- データ増加に伴い高価なメモリを増設し続ける必要がある
- **Snowflake / Databricks** 等のモダンデータプラットフォームはコンピュートとストレージが完全分離
- 安価なクラウドストレージにテラバイト級データを貯め、分析時だけコンピュートを立ち上げる — ビッグデータ分析で圧倒的なコストパフォーマンス

### コンポーザブル ERP（適材適所の組み合わせ）

- ERP にすべてのデータ（非構造化、IoT、他システム）を詰め込む「モノリス型」は過去のもの
- **コア ERP（SAP / Oracle）** — SoR（System of Record）。財務数値の正確性、受発注の実行、リアルタイムな一次集計に徹する
- **データプラットフォーム（Snowflake / Databricks）** — SoI（System of Insight）。ERP データに外部市場データ・Web ログ・センサーデータを統合し、AI/ML による需要予測や高度な予実管理を行う
- **データ連携の具体像** — SAP SLT、ETL と ELT の違い、レプリケーションと CDC の考え方

## 第5章：ERP とデータプラットフォームの連携設計

第4章で触れた SoR / SoI の切り分けを、実際のデータフローとしてどう実装するかを学ぶ。

### 複製・抽出の方式（SAP 中心）

- **SAP SLT（SAP Landscape Transformation）** — S/4HANA から分析基盤へテーブル単位でリアルタイム複製する仕組み
- **ODP（Operational Data Provisioning）** — 抽出オブジェクトと Delta 更新の考え方。どのデータを「いつ・どの粒度」で出すか
- **バッチ ETL の位置づけ** — 夜間フルロードが残る領域（レガシー連携、大量履歴の初回投入）と、リアルタイム化すべき領域の見極め

### ETL・ELT・CDC の違い

- **ETL（Extract → Transform → Load）** — 変換を中間サーバーで行いから DWH へ載せる古典型。R/3 時代の鉄板パターン
- **ELT（Extract → Load → Transform）** — 生データをいったんレイク／ウェアハウスに載せ、SQL や Spark で変換するモダン型
- **CDC（Change Data Capture）** — 差分だけを追跡し、基幹の負荷とレイテンシを抑える。イベント駆動連携の前提
- **レイテンシと整合性** — 秒単位の複製が必要な領域（在庫・売上ダッシュボード）と、日次で足りる領域（経営集計）の設計判断

### API・イベント・iPaaS による連携

- **OData / REST API** — トランザクション単位・マスタ参照向け。ボリュームが大きい分析用途には不向きな理由
- **メッセージング（キュー・イベントバス）** — 受注確定・出荷完了など「業務イベント」を他システムへ非同期通知
- **iPaaS（Integration Platform as a Service）** — MuleSoft、Boomi 等が担うマッピング・オーケストレーションと、ERP コアを汚さない境界

### データレイクハウスとメダリオンアーキテクチャ

- **Bronze / Silver / Gold** — 生データ → クレンジング済み → ビジネス向け集計の段階的品質管理
- **レイクハウス** — データレイクの柔軟性と DWH の SQL 分析を統合する考え方（Databricks Delta Lake、Snowflake 等）
- **ERP データの置き場所** — 会計伝票・受注明細は Gold に近い層へ。IoT・ログは Bronze から始める典型

## 第6章：アーキテクチャ選定・ガバナンス・コストの観点

「どの製品が正解か」ではなく、要件と制約から全体像を評価するための枠組み。

### 選定の評価軸（3 つのレンズ）

- **プロセス統合度** — 全社で業務を揃える必要があるか（Fit to Standard の余地）、子会社ごとに最適化を許容するか
- **データ特性** — トランザクション量、保持年数、分析のリアルタイム性、非構造化データの比率
- **運用・コスト** — ライセンス、HANA メモリサイジング、クラウド egress、運用人員のスキルセット

### 2-tier ERP とハブ＆スポーク

- **2-tier ERP** — 本社・グローバルは S/4HANA、地域・子会社は軽量 ERP（Business ByDesign、クラウド SMB 系）という二層構成
- **ハブ＆スポーク** — 連結会計・EPM をハブに、各社のローカル ERP をスポークとして接続。M&A 後の統合に向くパターン
- **SAP と Oracle での設計難易度の差** — 単一 DB（SAP）とモジュール分散（Oracle）が、2-tier 設計に与える影響

### TCO とインフラのトレードオフ

- **HANA サイジング** — メモリに載せるデータ量、圧縮率、温冷データの扱い。肥大化時のランニングコスト急増
- **クラウド ERP（RISE with SAP 等）** — サブスクリプション型の OpEx 化と、カスタマイズ制約のトレードオフ
- **分析基盤の従量課金** — Snowflake / Databricks のコンピュート課金、ストレージ egress。使い方の設計がコストを左右する

### マスターデータとデータガバナンス

- **MDM（Master Data Management）** — 顧客・品目・勘定科目が複数システムに散在するときの「正」の定義
- **データカタログ・リネージ** — どのレポートがどの ERP テーブル由来かを追跡。監査・GDPR 対応の基盤
- **データ品質ルール** — 重複排除、必須項目、コード体系の統一。連携前より連携後の品質劣化を防ぐ

### Embedded Analytics の限界とモダンプラットフォームの境界

- **ERP 内分析で足りる領域** — 部門別予実、伝票ドリルダウン、Fiori 上のリアルタイム KPI
- **外に出すべき領域** — 他社データとの相関、機械学習、長期履歴の探索的分析、非 ERP データ（Web・IoT）の統合
- **「すべてを ERP に押し込まない」理由の整理** — コスト、硬直化、バージョンアップ阻害の三つを具体的に説明できること

### まとめ

- アーキテクチャは **SoR（堅牢なコア）** と **SoI（柔軟な分析基盤）** の二層で考え、連携方式・ガバナンス・TCO をセットで設計する
- ベンダー比較は「機能リスト」ではなく、**出自・ハードウェア史・データの置き場所**から説明できることが本コースの到達点
