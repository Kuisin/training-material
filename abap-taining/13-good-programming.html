適切なプログラミング

性能と保守性。10年後も使われることを見据えた、悪い例・良い例の対比で学ぶ仕上げの章です。

⏱ 25分📶 初学者🏷 ABAP研修

この章で学ぶこと

  • 性能（速さ）と保守性（直しやすさ）を両立する書き方
  • SELECT や LOOP の書き方で、なぜ速度に差が出るのか
  • 悪い例・良い例の対比と、引き継げるコードの条件

「近道」が、実は渋滞の原因になる

その場では速そうに見える書き方が、データが増えると一気に遅くなることがあります。とくに「DBへ何度も取りに行く」書き方は、件数が増えるほど効いてきます。

先生：性能は「少ないデータでは気づかない」のが怖いところ。本番の大量データで初めて遅さが牙をむきます。だから最初から良い型で書きます。
Bちゃん：少人数の試食会では平気でも、本番の宴会で回らなくなる…みたいなことですね。

DBアクセスは「往復」が重い

データベースへの問い合わせは、1回ごとに“往復の時間”がかかります。ループの中で毎回 SELECT すると、その往復が件数分くり返され、とても遅くなります。

つまずき：「LOOP の中で SELECT」は代表的なアンチパターン。件数×往復＝爆発的に遅くなります。
Aくん：計算量の話ですね。N件のループ内でN回問い合わせれば、コストはNに比例して膨らむ。

悪い例：ループの中で毎回DBへ

" ❌ 明細1件ごとにDBへ取りに行く（往復が件数分）
LOOP AT lt_bseg INTO ls_bseg.
  SELECT SINGLE butxt FROM t001
    INTO lv_name
    WHERE bukrs = ls_bseg-bukrs.
  WRITE: / ls_bseg-belnr, lv_name.
ENDLOOP.
Bちゃん：1件ごとに倉庫まで歩いて取りに行ってる…たしかに大変そう。

良い例：先にまとめて取り、メモリで突き合わせ

" ✅ 必要な会社名を一度だけまとめて取得
SELECT bukrs butxt FROM t001
  INTO TABLE lt_t001
  FOR ALL ENTRIES IN lt_bseg
  WHERE bukrs = lt_bseg-bukrs.

LOOP AT lt_bseg INTO ls_bseg.
  READ TABLE lt_t001 INTO ls_t001
    WITH KEY bukrs = ls_bseg-bukrs.   " メモリ内で照合（往復なし）
  WRITE: / ls_bseg-belnr, ls_t001-butxt.
ENDLOOP.
Aくん：先に倉庫から必要分を台車でまとめて運び、あとは机の上で照合。往復が激減しますね。
この章のABAPキーワード：FOR ALL ENTRIES / READ TABLE / 必要な列だけ SELECT / 性能・保守性。

図で見る：無駄な往復を減らす

先生：ポイントは「DBへの往復を減らす」「必要な列だけ取る」。この2つだけでも、体感速度は大きく変わります。

保守性：10年後も誰かが直せるように

  • コメント・命名：意図が読み取れる
  • 変更履歴：いつ・なぜ変えたか分かる
  • 開発標準に合わせる：チームで書き方を揃える
  • 部品化：直す範囲を狭く保つ
Bちゃん：速さだけじゃなく、優しさ（読みやすさ）も品質なんですね。
先生：速くて、読みやすくて、安全に直せる。この3つがそろって“適切なプログラミング”です。研修おつかれさまでした！
